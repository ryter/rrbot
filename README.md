# Исследовательский бот Rush Royale

Бот для исследования: распознаёт состояние поля, принимает решение о том,
кого и куда ставить, и (опционально) выполняет действия в клиенте игры.

В проекте два варианта:

* **C++ (`cpp/`)** — основной. Живой режим: бот сам проходит меню, читает
  энергию, зовёт юнитов. Работает и с веб-клиентом в браузере, и с
  мобильным клиентом в эмуляторе Waydroid. Подробности — `cpp/README.md`,
  состояние проекта и памятка — `HANDOFF.md`.
* **Python (`rrbot/`)** — прототип с симулятором: зрение, планировщик и
  режим живой игры в браузере. Измерения точности детекции сделаны на нём.

Сделан так, чтобы каждый шаг можно было **измерить**: есть симулятор с
эталонной разметкой, инструмент оценки точности детекции и режим живой
игры в браузере.

```
cpp/            основной бот на C++: живой режим (браузер и эмулятор)
rrbot/          прототип: зрение, планировщик, симулятор, живой режим
tools/          утилиты: шаблоны, калибровка, замеры, цифры, эмулятор
config/         конфигурация: default.yaml (симулятор), live.yaml (живая игра)
assets/         шаблоны юнитов, эталоны цифр, элементы интерфейса
tests/          модульные тесты
```

## Быстрый старт

### Основной вариант (C++)

```bash
cd cpp
make                                     # нужен OpenCV (opencv5) и libevdev
./build/rrbot --backend emulator --steps 40   # бой в эмуляторе Waydroid
./build/rrbot --backend adb --probe            # что бот видит в кадре
```

Документация по C++-боту — `cpp/README.md`.

### Прототип на Python

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

.venv/bin/python tools/make_templates.py     # сгенерировать эталоны юнитов
.venv/bin/python main.py                     # графический интерфейс + симулятор
```

Для кликов настоящей мышью нужен доступ к `/dev/uinput` (группа `input`):

```bash
sudo bash tools/setup_ydotool.sh   # правило udev и группа input
# после этого перезайти в сессию
```

Пакет `evdev` ставится вместе с остальными (`requirements.txt`).

Другие режимы Python-прототипа:

```bash
.venv/bin/python main.py --headless 600      # прогон без GUI (замеры)
.venv/bin/python tools/evaluate_vision.py --sweep   # точность детекции
.venv/bin/python tools/experiment.py         # сравнение настроек планировщика
```

У C++-бота есть свои режимы разбора — без запуска игры:

```bash
cd cpp
./build/rrbot --backend adb --frame f0102.png        # разбор сохранённого кадра
./build/rrbot --backend adb --digits-image f.png     # чтение числа из выреза
./build/rrbot --backend adb --steps 45 --rounds 3    # три боя подряд
```

## Как устроен бот

### Зрение (`rrbot/vision.py`)

* **Каноническое поле.** Кадр экрана приводится к прямоугольнику 334×254
  гомографией, поэтому детектор не зависит от разрешения монитора, размера
  окна и положения игры на экране.
* **Шаблоны.** Эталон типа юнита — только его тело, без фона поля. Иначе
  совпадение ломается о разную подложку (трава, река, мосты).
* **Сторона** определяется не по шаблону, а по оттенку насыщенных пикселей
  внутри найденного диска: глиф типа белый и в расчёт не попадает.
* **Подавление дубликатов** — NMS по IoU, общий для всех типов, чтобы один
  юнит не давал находку сразу от нескольких шаблонов.

### Планировщик (`rrbot/planner.py`)

Полезность каждого типа юнита — сумма взвешенных слагаемых:

| слагаемое | смысл |
|---|---|
| `counter` | перебиваем ли мы врагов этого типа (доля их урона) |
| `pressure` | насколько велик враг у выбранной линии |
| `synergy` | не забиваем ли линию одним типом |
| `cost` | эффективность по мане (по метрике `planner.cost_metric`) |
| `available` | юнит вообще доступен к спавну |

Метрика эффективности по мане выбирается в конфиге (`planner.cost_metric`):

* `hp` — живучесть на единицу цены;
* `hp_dps` — живучесть × урон на единицу цены, нормированные так же, как
  `hp` (значения сопоставимы, вес имеет один смысл).

Выбрана замером, а не на глаз: `tools/compare_cost_metric.py` гоняет обе
метрики в симуляторе на одних и тех же сидах. На частых волнах
(`--wave-size 4 --wave-interval 13`, 30 партий на пресет) `hp_dps` даёт
**99.0 % побед против 83.3 %** у `hp` и нигде не хуже; на обычных волнах
(из `config/default.yaml`) разницы нет — там решают контр-счётство и
правило выбора линии.

Отдельно реализовано **накопление маны**: если сейчас доступен только слабый
юнит, а недоступный дал бы заметно больше пользы, бот ждёт. Порог выигрыша
(`save_mana_min_gain`) тоже подобран замером: 1.5 даёт 98.9 % побед против
96.7 % у 1.0 и 90.0 % у 0.5 (слишком часто ждём зря).

### Выбор линии

Линия высадки выбирается в три шага:

1. если враг перешёл середину поля — защищаем его линию;
2. иначе толкаем в линию, где врага меньше (контр-пуш);
3. при равной угрозе — в ту, где меньше наших юнитов.

Правило 1–2 даёт в симуляторе 97.5 % побед против 35 % у прежнего выбора
«туда, где враг сильнее» (см. «Что измерено»). Высота поля, по которой
ищется середина, задаётся в конфиге (`planner.defend_line_height`).

### Симулятор (`rrbot/sim.py`)

Портретная арена с рекой и двумя мостами, волны врага, энергия, таймеры.
Нужен для двух вещей: эталонная разметка для оценки детекции и замкнутый
контур «решение → действие → исход» для сравнения конфигураций.

## Что измерено

Точность детекции на эталонной разметке симулятора
(`tools/evaluate_vision.py --sweep`):

| порог | recall | precision | тип | сторона | ошибка позиции |
|---|---|---|---|---|---|
| 0.55 | 0.979 | 0.243 | 0.976 | 0.989 | 1.28 px |
| 0.60 | 0.979 | 0.995 | 0.976 | 0.989 | 1.28 px |
| 0.65 | 0.978 | 1.000 | 0.977 | 0.989 | 1.28 px |
| 0.70 | 0.978 | 1.000 | 0.979 | 0.988 | 1.27 px |
| 0.72 | 0.978 | 1.000 | 0.979 | 0.988 | 1.27 px |
| 0.75 | 0.977 | 1.000 | 0.979 | 0.988 | 1.27 px |
| 0.78 | 0.977 | 1.000 | 0.979 | 0.988 | 1.27 px |
| 0.80 | 0.977 | 1.000 | 0.979 | 0.988 | 1.27 px |
| 0.85 | 0.977 | 1.000 | 0.980 | 0.988 | 1.27 px |

Порог 0.75 выбран по границе: ниже начинаются ложные срабатывания на
похожих силуэтах, выше — теряются юниты в движении.

Пропуски в детекторе — это не шум, а **наложенные спрайты**: два юнита рядом
дают одну находку, и второй теряется. Детектор теперь умеет разделять их:
спрятанный юнит ищется по «второму максимуму» отклика рядом с найденной
находкой и оценивается **по видимой части** (из шаблона выбрасываются
пиксели, закрытые соседями). Это подняло recall с 0.954 до 0.977 при
прежней precision 1.000 и уменьшило ошибку позиции с 1.66 до 1.27 px.
C++-порт даёт на тех же кадрах те же числа до последней цифры
(`tools/evaluate_vision_cpp.py --mode sim --compare`).

Замер на **настоящих** кадрах из эмулятора (`assets/eval_real`, 24 кадра,
483 юнита): веб-клиентные эталоны не подходят — при пороге 0.55 recall
0.580, но precision 0.106, то есть детектор находит шум. Свои эталоны
(`assets/real_emulator/`) дают на тех же кадрах precision 0.646 при recall
0.449 — в шесть раз чище. Ограничение набора: восемь типов из двух боёв,
а в замере юниты самых разных; ещё нужны кадры с других колод и разметка
с типами.

Чтение энергии в живой игре: значение считывается как **число** (в веб-клиенте
шкала декоративная), распознавание по эталонам цифр, погрешность — точно
при совпадении шаблона, иначе цифра помечается как нераспознанная. В
C++-боте число читается в два прохода: сначала яркое, а если его нет —
потускневшее (на потолке энергии цифры гаснут и сереют). Точность
зафиксирована регрессионным набором из 70 вырезов области энергии
(`assets/test_energy/`): читается 70/70, на прежних эталонах мобильного
клиента — 64/70.

### Планировщик против случайного выбора

Главный вопрос к планировщику: даёт ли он выигрыш или просто тратит энергию.
Замер в симуляторе (`tools/experiment.py`, 40 партий на стратегию, волны
заданы явно):

| стратегия | волны 5/12 | волны 4/13 | волны 3/14 (из конфига) |
|---|---|---|---|
| планировщик (веса из конфига) | **45.0 %** | **100.0 %** | 100 % |
| пресет `counter_heavy` | 37.5 % | 97.5 % | 100 % |
| случайный выбор карточки | 7.5 % | 52.5 % | 100 % |
| случайный из готовых и оплачиваемых | 7.5 % | 60.0 % | 100 % |

На обычных волнах выигрывают все (симулятор прост), поэтому различать
стратегии приходится на частых волнах. До починки выбора линии было наоборот:
случайный выбор выигрывал чаще планировщика (65 % против 35 %) — и вот
почему:

* волны врага идут по одной линии и числом превосходят наши подкрепления;
* юниты, отправленные в ту же линию, гибнут в стычке и не доходят до базы
  врага;
* поэтому, пока враг держится в своей половине, бот **не лезет в его линию**,
  а толкает в другую (контр-пуш), и только если враг перешёл середину поля —
  защищает его линию.

Замер этого правила (`/tmp` — скрипт абляции, 40 партий): контр-пуш с
защитой — 97.5 % побед, выбор линии по давлению — 35 %, случайный выбор —
70 %. Правило устойчиво: на пороге середины поля (y > 320) выигрыш 100 % на
волнах 3/14 и 4/13, на самых тяжёлых 5/12 — 63 % (против 20 % при пороге
576).

Побочный эффект, который стоит понимать: в симуляторе кандидат к призыву
почти всегда один — хватает маны ровно на одного юнита, — так что веса
(`counter`, `pressure`, `synergy`, `cost`) влияют на выбор лишь изредка.
Поэтому сравнивать наборы весов имеет смысл только на частых волнах.

## Живая игра (веб-клиент в браузере)

Ниже — как это устроено в Python-прототипе. В C++-боте правила те же, но
описаны в `cpp/README.md`; там же — мобильный клиент в эмуляторе.

Rush Royale играется в браузере на `store.my.games`. Бот умеет:

* снимать кадр окна игры (`grim` для Wayland, `mss` для X11);
* находить область игры по рамке на экране — окно можно перемещать;
* находить элементы интерфейса по цвету: крестик, «Продолжить», PvP, «Бой»;
* вырезать поле, распознавать юнитов и читать энергию;
* кликать по карточке юнита и точке высадки.

Ввод — только виртуальной мышью (см. ниже): DevTools Protocol из проекта
убран.

### Ввод

Единственный способ ввода — **виртуальная мышь**. Бот создаёт своё
устройство uinput с осями `ABS_X/ABS_Y` и кликает им по экрану: курсор
виден, попадает пиксель в пиксель, работает с любым приложением —
включая нативный клиент игры.

Нужны доступ к `/dev/uinput` (группа `input`) и пакет `evdev`:

```bash
sudo bash tools/setup_ydotool.sh   # правило udev + группа input
# после этого перезайти в сессию
```

Проверено: `ydotool mousemove --absolute 500 500` уводил курсор в
(1000, 1000) — виртуальное устройство объявляет координаты вдвое
меньше экрана. Своё устройство с абсолютными осями такой ошибки не
имеет.

Раньше был ещё путь через DevTools Protocol, но он убран: клики в
браузере невидимы (курсор не двигается) и работают только внутри
вкладки. Теперь Chrome можно запускать как обычно — без
`--remote-debugging-port`.

Положение холста бот находит **по рамке на снимке экрана** (тёмно-синяя
полоса вокруг игры), а положение окна — у композитора. Поэтому окно
можно перемещать и менять размер: бот подстроится сам.

### Настройка живой игры

1. Запустить Chrome и открыть игру:

   ```bash
   google-chrome-stable --user-data-dir=/tmp/rr-chrome
   # дальше открыть https://store.my.games/app/5356
   ```

   Отладочный порт не нужен: бот смотрит в экран и кликает настоящей
   мышью.

2. Снять эталоны юнитов с настоящего поля:

   ```bash
   .venv/bin/python tools/collect_real_templates.py /tmp/opencode/m_07.png
   ```

   Файлы кладутся в `assets/real/`. Сопоставление «тип → файл» задаётся
   в `config/live.yaml` (`vision.template_map`).

3. Обучить цифры (энергия в веб-клиенте выводится числом):

   ```bash
   .venv/bin/python tools/observe.py --seconds 120        # записать игру
   .venv/bin/python tools/label_batch.py \
       --frames /tmp/opencode/observe/frames/f0000.png ... --values 60 80 110
   ```

4. Запустить:

   ```bash
   .venv/bin/python main.py --config config/live.yaml
   ```

   В интерфейсе выбрать источник «Живая игра (браузер)».

   Либо прогнать бот без интерфейса:

   ```bash
   .venv/bin/python tools/autoplay.py --steps 30
   ```

### Что проверено на живой игре

| возможность | результат |
|---|---|
| захват окна игры (`grim`, Wayland) | работает; `mss` на Wayland даёт чёрные кадры |
| поиск кнопок меню по цвету | крестик модальных окон, «Понятно», «Продолжить», PvP, Co-Op, «Отмена» находятся |
| проход по меню до матча | проходит окна наград, сундуков и предложений, затем PvP; повторяет при «противник не найден» |
| чтение энергии (цифры) | верно на боевых кадрах; область не обрезается, иначе «5» читается как «8» |
| распознавание юнитов на поле | совпадение 0.55-0.72 по настоящим шаблонам (32 эталона) |
| различение сторон | по положению на арене: верх — противник, низ — свой |
| кнопка призыва | карточка в виджете маны над рядом карточек, `(228, 685)` |
| цена призыва | виджет показывает её сам и гаснет, когда энергии не хватает |
| призыв юнита | энергия падает ровно на цену из виджета (10, 20, 30 …) |
| клик настоящей мышью (uinput) | курсор попадает в цель пиксель в пиксель; кликает и веб-клиент, и любой другой |
| работа без DevTools Protocol | Chrome запускается как обычно; холст бот находит по рамке на экране |
| окно перемещается и меняет размер | бот сам находит окно и холст заново (проверено на развёрнутом окне) |
| автобой подряд | проходит меню, читает ману, зовёт юнитов, ждёт регенерации |

### Механика призыва в веб-клиенте

Кнопка призыва — **не** карточка в ряду и **не** юнит на поле, а карточка
в **оранжевом виджете с значком маны**, который стоит **выше** ряда карточек,
внизу экрана. Нажатие тратит ману и призывает доступного юнита.

Что выяснилось при разборе живых боёв:

* **цена призыва — в виджете, а не в колоде.** Число рядом с флаконом в
  виджете — цена следующего призыва (10, 20, 30, 40, 50 … — цена растёт
  от призыва к призыву). Числа под карточками колоды — стоимость
  **улучшения** юнита, к призыву они отношения не имеют;
* **виджет сам показывает, хватает ли энергии:** когда хватает — он
  оранжевый, когда не хватает — серый, и цифра в нём гаснет. Это надёжнее,
  чем распознавать цифры чужого шрифта, поэтому бот решает «звать или
  ждать» по цвету виджета, а не по цене из конфига (конфиг описывает
  симулятор);
* энергия в HUD выводится **числом**, шкала декоративная — читать надо
  цифры. Область чтения — `(138, 682, 38, 16)`; обрезать её снизу нельзя:
  срезанный низ цифры превращает «5» в «8» (число 50 читалось как 500);
* **карточки колоды не выбираются:** клик по ним открывает подсказку
  «Улучшить», виджет от этого не меняется. Выбора юнита в этом клиенте
  нет — призывается тот, кого показывает виджет.

Цикл бота:

1. прочитать энергию (число рядом с голубым флаконом);
2. оценить поле: свои и чужие юниты, количество противников;
3. посмотреть виджет: оранжевый — призываем, серый — ждём;
4. нажать карточку в виджете и убедиться по свежему кадру, что энергия
   списалась.

Координата кнопки в каноническом холсте — `(228, 685)`; проверено на живых
боях: после нажатия энергия падала ровно на цену из виджета.

Особенности веб-клиента, которые пришлось учесть:

* кнопка «Понятно» в диалогах — синяя плашка, жать надо **нижнюю** её
  часть: центр плашки на ~20 px выше активной области;
* модальные окна (награда, сундук поддержки, предложения) закрываются
  **красным крестиком у заголовка** — он бывает на разной высоте, искать
  его надо по правому краю, а не по углу экрана;
* сервер PvP часто не находит соперников — нужен запасной режим Co-Op и
  кнопка «Отмена» на экране подбора;
* **критично:** экран подбора соперника анимируется, и «изменился ли экран»
  по кадру всегда истинно — навигация поэтому проверяет эффект клика и
  исключает бесполезные кнопки;
* стороны не различаются по цвету (фигурки юнитов тёплые у обеих сторон) —
  только по положению на арене.


## Мобильный клиент в эмуляторе

Основной бот на C++ работает и с мобильным клиентом, запущенным в Waydroid:
кадр берётся из устройства (`adb exec-out screencap`), клик — либо через
`adb shell input tap`, либо настоящей мышью по окну эмулятора (тогда клик
видно на экране).

```bash
cd cpp
./build/rrbot --backend emulator --steps 40   # клик мышью по окну
./build/rrbot --backend adb --steps 40        # клик через adb
./build/rrbot --backend adb --steps 45 --rounds 3   # три боя подряд
./build/rrbot --backend adb --frame f0102.png        # разбор сохранённого кадра
./build/rrbot --backend adb --digits-image cut.png   # чтение числа из выреза
./build/rrbot --backend adb --vision                 # разбор поля и подсказка
./build/rrbot --backend emulator --steps 40 --show   # окно с отметками кликов
```

Ключ `--show` открывает окно, где видно, куда бот нажимает (красный круг
и подпись элемента). Если окно открыть не вышло, кадры с отметками
складываются в `--out`.

**Слияние пешек.** Бот ищет на поле юнита, для которого в колоде есть
карточка, и перетаскивает карточку прямо на него — в Rush Royale одинаковые
юниты, поставленные друг на друга, сливаются в одного сильного. Соответствие
«эталон юнита → карточка в колоде» читается из
`assets/real_emulator/types.tsv`, а положение пешки пересчитывается из
канонического поля обратно в кадр. Если карточка на перезарядке, бот это
видит по тому, что энергия не упала, и возвращается к обычному призыву.

Правила работы бота проверяются офлайн, без игры: набор записанных кадров
с ожидаемым действием (`assets/test_nav/`) и проверка
`tools/check_nav.py` (29 из 29), набор вырезов области энергии
(`assets/test_energy/`) и проверка `tools/check_digits.py` (70 из 70).

Под мобильный клиент сняты свои раскладки (`cpp/src/layout.cpp`): у него
другое положение HUD, поля и карточек, а окно модального диалога шире —
поэтому порог, ниже которого крестик закрытия считается «не у правого
края», свой (0.60 против 0.78 у веб-клиента).

Что важно знать про окружение (подробности — в `HANDOFF.md`):

* сеть контейнера чинится скриптом `tools/waydroid_net.sh` — без него в
  контейнере не резолвятся имена и игра висит на «Проверка обновлений»;
* закрытие окна Waydroid уводит контейнер в заморозку, после чего
  `screencap` отдаёт пустой файл — лечится перезапуском контейнера;
* изменение размера окна меняет разрешение Android, а эталоны цифр собраны
  под 941×1030 — вернуть: `adb shell wm size 941x1030`.

## Ограничения и честные замечания

* **Реальные клики выключены по умолчанию.** `allow_input: false` в конфиге:
  бот считает и показывает рекомендации. Включать только на своём устройстве
  и в своей копии игры — автоматизация может нарушать правила игры.
* **В живом клиенте бот не выбирает юнита.** Карточки колоды не
  переключают призыв (клик открывает подсказку «Улучшить»), поэтому виджет
  сам решает, кого звать. Планировщик по-прежнему считает, какой юнит
  выгоднее, — но это подсказка, а не команда игре.
* **Эталоны юнитов для живой игры требуют ручной вычитки.** Автоматический
  сбор grabs ещё и элементы интерфейса; отбирать нужно вручную.
* **Калибровка поля в живом режиме задана константами** в `rrbot/live.py`
  (`FIELD_QUAD`, `ENERGY_REGION`, `CARD_ROW_Y`). Для другого разрешения
  окна или другой версии клиента их нужно пересчитать. Область чтения
  энергии обрезать нельзя: срезанный низ цифры меняет «5» на «8».
* **Распознавание типа юнита в живой игре** опирается на цвет основания и
  форму спрайта; полноценная классификация по колоде требует доработки.
* **В C++-боте распознавания типов юнитов и планировщика пока нет** — там
  только «звать, когда хватает энергии» (порт `rrbot/vision.py` и
  `rrbot/planner.py` идёт, но в живой цикл ещё не включён). Под мобильный
  клиент сняты свои раскладки (`cpp/src/layout.cpp`) и свои эталоны цифр
  (`assets/digits_emulator`).
* **Эталоны цифр мобильного клиента завязаны на разрешение** 941×1030:
  изменение размера окна Waydroid меняет разрешение Android, и цифры
  перестают узнаваться. То же с набором вырезов для проверки:
  `assets/test_energy/`.
* Симулятор — не точная копия игры: в нём нет слияния юнитов, уровней
  карт и особых эффектов. Он нужен для измерений, а не для имитации баланса.
